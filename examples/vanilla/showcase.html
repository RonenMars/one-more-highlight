1 Two terms, two colors

The term selector picks out every match of one search word, so a single pass can paint each term differently. 

// one instance, one pass, two terms
h.mark(['ipsum', 'dolor'], { states: [
  { name: 't-ipsum', term: 'ipsum' },
  { name: 't-dolor', term: 'dolor' },
]});

4 RegExp search words & case sensitivity

A search word can be a RegExp, not just a string. Strings are escaped by default (autoEscape), so regex metacharacters in user input are literal. 

h.mark([/\d+(\.\d+)?/g, /\b[A-Z]{2,}\b/g], { states: [
  { name: 'rx-num',  term: 0 },   // term can be an index into searchWords
  { name: 'rx-caps', term: 1 },
]});

5 Bring your own matches

markRanges() takes precomputed offsets instead of searching — for hits from a server-side matcher, a search service, an NLP tokenizer, or AI citations. h.text exposes the flattened text the offsets index into.

6 Matching across element boundaries

The walker flattens every text node under the root before matching, so a phrase broken up by inline markup is still one match. This is the thing a string-based highlighter cannot do. 

h.mark('an element boundary')  // → 1 match, spanning 3 text nodes

A phrase can cross an element boundary and still count as a single match.

8 Excluding parts of the subtree

<script>, <style> and <noscript> are always skipped. A filter excludes anything else — here, the blockquote. 

new Highlighter(el, {
  filter: (node) => !node.parentElement.closest('.skip'),
});
